# Fusion workers

Status: current
Owner: src/tools/fusion/

Fusion delegates bounded task waves to worker turns. Contracts carry deliverables, declared inputs and dependencies; only a `file` provide a sibling requires orders the fan-out — its consumer runs in a later wave, even when the provider failed — while a symbol, id, endpoint, env, flag or other is an interface both sides code against at once, and the consumer's brief says it is written meanwhile (k8c lost about 130 s to a symbol wave, 16-11-2026). Preserve task status attribution and hand-back based on completed-step progress rather than an independent timer.

Workers are ephemeral: no durable session row/reflection/trace; no recursive delegation or invisible interactive approval. Provider pins must not fall over to a different billing/model leg. Declared input replacement remains forbidden. A worker's approval-gated call is refused by its session policy. A fan-out's directory covers its writes and ordinary commands there, never a dangerous command (`shell_dangerous`), the agent's own config or secret files (`trust_config`, `state_secret`), mail, passwords or payments: those are refused with `FUSION_WORKER_OPERATOR_ONLY_REFUSED`, and the task comes back `needs_orchestrator` with a note telling the orchestrator to hand the step to the user instead of re-sending it (ATO-1222, ATO-1223). A fan-out whose write scope lies inside the agent's own state directory (`~/.atomic-agent`) is refused before the operator is asked, and the worker brief says an operator-only refusal is reported, not sent back for a re-send (ATO-1267). A worker whose parent works outside the whole write scope (a session started in home, which the scope drops as too broad) runs in the scope's single root instead, with its declared files resolved against the parent's directory first (`workerHomeFor`); with several roots it keeps the parent's directory. The brief carries that directory's top level as the worker is dispatched (`AT START`, `renderStartListing`; `.git` left out, at most 40 names), so a first step need not list it — k8d's two workers spent 36 s listing an empty folder, 16-11-2026. Concurrency is resolved from the call, task count and serving slot capability, rather than blindly capturing startup state.

After a local worker is cut off (time limit, queue wait, hand-back or operator cancel), the next local dispatch first asks the server `GET /health` ([local-leg-health.ts](local-leg-health.ts), ATO-917); a server that does not answer fails the task at once with a restart hint instead of letting it wait out its budget. A server that does answer gets the worker on fresh connections: the process's HTTP pool is swapped for a new one first (`renewTransportPool`, ATO-1357), the part of an agent restart that cleared the field case, while requests already in flight keep their sockets. A worker that still gets no token while `/slots` shows every slot idle is told the request got stuck on the agent's side, not to restart the server.
Worker spend is priced per completion with the prompt-cache discount (`estimateUsageCostUsd`, ATO-918). With `llm.runMode.fusion.turnBudgetUsd` / `turnTimeBudgetMs` set, [turn-budget.ts](turn-budget.ts) caps a fusion turn (ATO-947): reset at the turn's start, checked before a delegation, before each worker starts and on every worker completion; reaching it stops running workers and returns a plain-words instruction to the orchestrator. Unset, none of it runs.

[failure-breaker.ts](failure-breaker.ts) stops a fan-out that keeps failing the same way (ATO-1406): one blocker (tool-call protocol mismatch, CLI missing or signed out, out of credit) or `REPEAT_FAILURE_STREAK` identical failures in a row on a leg, and no new task starts there; running workers finish. Trips are kept on the turn's `FusionTurnBudget`, and a later delegation is refused on a leg that hit a blocker, or after the same repeat stopped two rounds. The same state counts rounds and tasks against `maxRoundsPerTurn` / `maxTasksPerTurn` (defaults 6 / 48, `0` off), checked before the fan-out's approval; the approval line names the round and the task count. Both need the runtime's per-turn `turnBudget`.

[escalation.ts](escalation.ts) escalates a stuck worker (ATO-942): with `escalation: "advisor"`, the first stall or cut first answer asks `ResolvedRunMode.escalation` (a configured provider other than the worker leg) for a hint at most `ADVISOR_MAX_OUTPUT_TOKENS` long, refused when its worst case is over `escalationMaxUsd`, and steers the worker with it. A later stall re-runs the task on that model only with `escalationReplace`. `FusionLiveWorkers` exposes the person's stop / escalate / steer per running worker (ATO-66, ATO-568), keyed by parent session and task id; a person's note rides the shared steering inbox under the worker's ephemeral session id and is read at its next step boundary. `src/http/route-fusion-workers.ts` puts the same three calls on HTTP for the desktop. Escalation spend is added to the turn's cap and reported per row and per fan-out.

[judge.ts](judge.ts) is the trimmed judge (ATO-944, `judge: "on"`): an acceptance list per task, rendered read-only into its brief (`briefSuffix`); after the waves, facts (check outcomes, provide presence, declared files) decide their items and can only be red or green on their own; a fresh-context judge (no transcript; files, or the reply when no file was declared) rules on the rest, in one call per round for all of a fan-out's judgeable tasks (`judgeTasks`: the preamble, the original request and a file two tasks share are sent once, the evidence budget grows by `JUDGE_EVIDENCE_EXTRA_CHARS` per further task, items are named `<task>:<item>`, and the call's cost is split evenly; k3a paid two calls of 7-9k written tokens each, 15-11-2026). The call is built to be cached (the judge was 0.39 of k3c's 0.70, 16-11-2026): it opens with the same rules every time (`JUDGE_RULES`, up to `JUDGE_FIXED_PART_END`, which a vendor CLI provider puts in its system prompt), and the files are shown against a snapshot `fusion.delegate` takes of the declared paths before the work: a new file, or one of at most `JUDGE_WHOLE_FILE_CHARS`, whole; a larger changed one as a diff with `JUDGE_DIFF_CONTEXT_LINES` lines of context; a larger unchanged one by name only. Both rounds run in one CLI session (`JudgeSession`, keyed `judge-<uuid>` and passed as `cliSessionKey`): the retry round's prompt is the first round's plus a follow-up with the findings, the items to rule on again and only what changed since the ruling, so the first round is read from cache. A red item's `why` is at most about 20 words, and a later item that fails for the same defect says only `same as <id>`. It answers `{"red":[{id,why}],"pass":[id]}`, a reason only for red; an item named red, or named nowhere, is red, and the older `{"items":[…]}` form passes only a literal `pass: true`. Beside the files it reads the runtime's own record of the task's workers (`renderRuntimeRecord`): the paths their file tools wrote, a retry's added to the first attempt's, and each shell run that reached its exit, oldest first, up to six distinct command lines (`WORKER_RECORDED_RUNS`), with its exit code and the end of its stdout (a worker that ran pytest and then counted lines was ruled "pytest did not run" while the record held only the last command, ap3i) — so a step of process such as "run pytest and report the result" can be shown met (ap2c, 15-11-2026). When the session has an original request (`resolveOriginalRequest`), the judge reads it too (up to `JUDGE_REQUEST_CHARS`) and the list gets one last `request` item: an exact name, message, output line or format the request fixes is used verbatim, whatever the brief says (ap3b, 15-11-2026). The judge fails an item only for a defect in what the user gets — wrong or missing behaviour, a missing or wrong file, function or test, a name or output that differs from the request, a required run that failed — and passes style the request does not ask for, naming it in `why` (`JUDGE_SEVERITY_RULE`; ap3h re-ran a working package for comments and import form, 15-11-2026). A check the brief told the worker to run is a means: when the runtime's verify passed, not running it is not red by itself (k8c, 16-11-2026). A split task's subtasks have no record under its id, and the judge then gets none. A red list re-runs the task once with the findings, briefed as a repair (`renderRetryFindings`): only the lines the findings name, no new file unless one is asked for, the task's check at most once (k8c's two retries took about 17 steps each, 16-11-2026); the contract is re-evaluated on the retried rows only. A retry that comes back unjudgeable (failed, cancelled, no changes) keeps its status, and its row carries the first verdict as `judge` and names the red items and why in its note (ap1d, 15-11-2026). Unreadable or impossible judging leaves the task `needs_orchestrator`, never `ok`. A verdict on evidence cut to its budget carries `clipped: true` (kept into the follow-up round). A retry's `unchanged by this task` note keeps only paths the first attempt left unchanged too (`unchangedAcrossAttempts`).

[request-names.ts](request-names.ts) is the runtime's name check, before the judge and without a model: after each worker step that wrote, the runner compares the worker's written files with the names the original request writes as calls (`gem(opgaver)`). A name its files define or call one character off (`def sem(`, `.sem(`), or the same snake_case name with one part swapped for a word starting with the same letter (`from_dict` for `fra_dict`, ap3h), while none of them uses the request's spelling, becomes one steer per pair, read at the worker's next step boundary; a name the request itself uses as a word, a common library name (`get`) or a pytest function (`test_dict`) is never flagged. A steer that arrives after the worker's turn has ended is lost, and the judge's `request` item stays the backstop (ap3d: `Lager.sem` for `gem`, 15-11-2026).

[replan.ts](replan.ts) is automatic replanning (ATO-941, `autoReplan: N`): dependents of a provider that did not close are held (`not started: held for the replan`), attempts per task are counted per turn in `FusionTurnBudget`, and `details.replan` lists pending and exhausted tasks; `src/agent/fusion-replan.ts` holds the planner's next step to `fusion.delegate` while any are pending, for at most two steps without a fan-out.

[autoverify.ts](autoverify.ts) is autoverify (lever F1), off by default: `llm.runMode.fusion.autoVerify: true` (env `ATOMIC_AGENT_FUSION_AUTOVERIFY=1|0` wins) gives `fusion.delegate` an optional `verify` (verify.run's args) and one description sentence; flag off, schema and description are byte-identical. After the workers it runs `verify` through `dispatchNestedToolCall` (refusal, hooks, read scope, input-file protection, approval, cancellation as for a model-emitted `verify.run`), hands a failure to one local repair task, and verifies again, up to `autoVerifyRounds` (0..5, default 2). With the judge on, the verify runs once before each judge round instead (k8b, 16-11-2026: a tests task was red for "tests not run" and a NameError reached no retry): the judge reads it after the records (`renderVerifyRun`, never in `JUDGE_RULES`), a red task's retry brief gets its failure lines (`renderRetryFindings`), a retry voids it, and autoverify takes the last one as its first round (`prior`). A repair task gets at most 12 steps (`AUTOVERIFY_REPAIR_MAX_STEPS`, less if `workerMaxSteps` is smaller), and its brief lists the lines the work added (`path:line + text`, at most 40) with a hint that a failing check the work did not touch was most likely broken by them. A verify that did not run (denied, blocked, cancelled) stops the loop. The output opens with one `autoverify:` block (PASS/FAIL/NOT RUN, rounds, exit code, at most 30 failure lines, diff stat of the declared files; capped at 4000 chars) and `details.autoverify`. First round only, `reusableWorkerRun` takes the worker's own passing `os.shell.run` instead of a new verify (one task, one ok result; `WorkerRunCollector.lastCommand()` via `onWorkerCommand`): same command line (no shell syntax, no argument with a space, no `env`), same directory inside the working dir, exit 0, not timed out, no foreground-job detach, within the verify's timeout, no tool after it that can change files, and only `exit 0`/`exit == 0`/`stdout contains` checks, judged on its last 4000 stdout chars. The block then says `reused the worker's own passing run` and `details.autoverify.reused` is true. A reused pass skips the throwaway copy and the soft network block that `verify.run` adds; any doubt runs the real verify. [reviewed-note.ts](reviewed-note.ts) puts one `reviewed:` line under the block (and `details.reviewed: true`) only when every row is `ok` and judge-green on unclipped evidence with at least one item ruled `by: "judge"` and none skipped, the verify passed with no repair, and nothing is unsettled (cancel, budget stop, breaker, replan, resume, merge); it tells the orchestrator not to re-read the diff (k3d, 16-11-2026).

[role-models.ts](role-models.ts) is models by role and node (ATO-943): `llm.runMode.fusion.roles` maps `plan / build / review / explore / utility` to configured providers (one entry = one model). A task's `model` (must be the worker leg or a role model, else the call is refused) wins over its `role`, which wins over the worker leg. Each leg's tasks run as their own group (cloud cap for a cloud leg, one at a time on a second local server), priced, counted in the turn's cap, and the row carries `model` / `modelRole`. A second llama-server model is used only with `mixLocalModels: true`; otherwise the task runs on the worker leg and its row says so. `review` is the judge's model when `judgeProvider` is unset; `plan` does not switch the orchestrator. The `### fusion` block lists the role models only when some are configured.
[branch-workspace.ts](branch-workspace.ts) and [branch-merge.ts](branch-merge.ts) are branch isolation (ATO-946, `isolation: "worktree"`, default `"off"`): each run of tasks (a wave, a judge's retry) gets a workspace per task plus an untouched base, all from one snapshot of the working directory. In a git repo the snapshot is `git stash create` (HEAD when clean; the working tree, index and stash list are not touched) checked out as a detached `git worktree`, with untracked files copied and ignored directories symlinked; elsewhere it is a folder copy (clonefile on macOS); a tree too large to copy runs in place and every row says so. The worker's session, brief, write scope, declared inputs and declared-file check all point at its workspace (`RunWorkerTasksOptions.taskWorkspace`). After the wave each workspace is merged back in task order, file by file against the base: a file only the task changed is copied in, one the folder also changed is merged with `git merge-file`, anything else is a conflict that leaves the folder's file untouched, saves both sides under `.atomic-agent/fusion-merge/`, turns the row `needs_orchestrator` and returns a `merge-<id>` task in `details.merges` for the planner. A declared input the task removed or cut to under half its lines is refused at merge time. Failed, cancelled, timed-out and queued tasks are not merged. Workspaces are removed (`git worktree remove --force`, `git worktree prune`) in a `finally`, on abort and throw too.
[task-tree.ts](task-tree.ts) is the task tree (ATO-940, `taskTree.enabled`, default off; `maxDepth` 2, hard cap 3; `maxNodes` 24). Workers still never delegate: a worker that may split is told how in its brief and steered once at the half-budget hand-back or a cut first answer (`SPLIT_GRACE_STEPS` more steps), and ends its turn with a fenced `split_proposal`. The delegate validates it with `parseDelegateArgs` plus the depth, node and parent-files caps, namespaces ids as `parent/child`, runs the children through the same runner (turn caps, approval scope, child budgets clamped to the parent's), checks their contract and the parent's declared files, and closes the parent row on them. A refused proposal leaves the task `needs_orchestrator`. `details.taskTree` carries the nodes.
[run-checkpoint.ts](run-checkpoint.ts) and [run-resume.ts](run-resume.ts) let a run survive a restart (ATO-617): one JSON file per run under `<stateDir>/fusion-runs/` (not a table: the session store's schema and turn marks are pinned, and a checkpoint write must never fail a fan-out), written after every finished task (row, spend, side-effect tools as they start) and every wave, deleted on a normal end, kept as `interrupted` when the turn was stopped. A file whose process is gone or stopped is offered (`runtime.fusionRuns`, `/fusion` in the TUI) for 7 days. `fusion.delegate { resume: runId }` replays the checkpoint's own arguments: settled tasks are carried (a `cancelled` row is not settled), the rest run, the spend so far counts toward the turn's cap, and a task whose worker called anything outside the file tools and reads (`toolHasSideEffects`) is not re-run until `confirm: [taskId]`.
